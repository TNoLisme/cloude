## 1. Quan hệ với v1 và phạm vi

Giữ nguyên [[digitalbanking-docs/docs-common/07. API contracts.md]] và [[digitalbanking-docs/openapi/digital-banking-v1.yaml]]. V2 kế thừa danh mục 30 operations, schema/request/response/ngữ nghĩa của v1 tại thời điểm tách (OpenAPI 1.0.0, SHA256 `71EFC546FB6645BE128EC83D391706343A6FF6B1FA6991910E42770D62EF796A`), với các thay đổi được liệt kê đầy đủ tại mục 2. Các path dưới đây tương đối với `/api/v2`; không sửa đường dẫn runtime v1 hoặc coi BE v2 đã tồn tại. Sau này mỗi thay đổi phải đồng bộ ngữ nghĩa và YAML của đúng version, không tự propagate qua v1/v2.

Các giới hạn đang đề xuất và open issues của v1 vẫn mở ở v2 nếu không có quyết định riêng. Không tự bổ sung API legacy register/recovery/PIN/create customer/seed/block/unblock; chúng thuộc đợt tích hợp đầu nhưng chờ BE/BA cung cấp contract.

## 2. Delta Security của v2

| Nội dung | V1 giữ nguyên | V2 mục tiêu FE/mock |
|---|---|---|
| Base URL | `/api/v1` | `/api/v2` |
| Cookie session | `DB_SESSION`, `Path=/` | `SESSION_TOKEN`, `Path=/api` |
| Thuộc tính cookie | Theo hợp đồng v1 | `HttpOnly; Secure; SameSite=Strict`, giữ chính sách TTL của nguồn; không tự chốt giá trị đang đề xuất |
| Login challenge purpose | `LOGIN_NEW_DEVICE` | `LOGIN_MFA` |
| Purpose khác | `TRANSFER_STEP_UP`, `SENSITIVE_ACTION` | Giữ nguyên |
| Auth response JSON | `user`, `session`, `correlationId` | Giữ nguyên; không trả raw session token/accessToken legacy trong JSON |
| CSRF | Lấy từ login/session; header X-CSRF-Token cho request ghi dùng cookie | Giữ nguyên |
| Logout | POST /auth/logout, thu hồi session và xóa cookie v1 | POST /auth/logout, thu hồi session v2; xóa đúng cookie SESSION_TOKEN với Path=/api |

Ví dụ header v2 (TTL cụ thể vẫn theo chính sách cần owner xác nhận):

```http
Set-Cookie: SESSION_TOKEN=<opaque>; HttpOnly; Secure; SameSite=Strict; Path=/api
Set-Cookie: SESSION_TOKEN=; HttpOnly; Secure; SameSite=Strict; Path=/api; Max-Age=0
```

Frontend không đọc hoặc tự cấp cookie HttpOnly. Credentials include cho request; metadata người dùng/CSRF chỉ giữ trong memory. GET /auth/session phục hồi metadata khi reload; POST /auth/logout có CSRF theo contract. 401 AUTH_OTP_INVALID ở challenge không được đồng nhất với hết session.

LOGIN_MFA là purpose của login challenge cho các vị trí v1 dùng LOGIN_NEW_DEVICE, gồm login/verify OTP/resend và nhánh login FIDO đã được mô tả. Không tự chốt provider/enrollment, FIDO ceremony hoặc tên purpose mới khác ngoài delta này.

## 3. Danh mục và kiểm chứng

Danh mục operationId/method/request/response giống snapshot v1 ở mục 1; schema/session cookie/purpose và server URL đã được thay rõ trong YAML v2. Money/ID, pagination, role/privilege, error codes, transfer idempotency và approval/fraud/audit không thay ngoài base path. Tests contract phải kiểm tra không phát sinh delta không được liệt kê.

Sinh types v1 và v2 riêng; mỗi client/mock chọn đúng version. Không sửa types generated bằng tay. Mock v2 có nhãn fixture và không chứng minh HttpOnly, Secure, cookie jar, DB session, audit hoặc CSRF của server thật.

## 4. Migration và điều kiện tích hợp còn mở

| ID | Việc cần BE/Security/DB xác nhận |
|---|---|
| V2-01 | Publish/routing readiness của /api/v2, bảo đảm v1 vẫn hoạt động theo contract cũ |
| V2-02 | Mapping/migration purpose LOGIN_MFA với constraint DB hiện mô tả LOGIN_NEW_DEVICE; không tự sửa DDL/seed theo lựa chọn FE |
| V2-03 | Coexistence hai cookie/session version, chính sách logout/revoke/expiry và tránh chọn nhầm cookie khi request có cả hai |
| V2-04 | Cookie Secure/HttpOnly/SameSite/Path thực, HTTPS/CORS/CSRF topology, reload/logout trên browser |
| V2-05 | BE/Security review ngữ nghĩa/header/examples và xác nhận contract trước integration |

GAP-05 chưa đóng khi chỉ có tài liệu/types/mock. Các mục trên không được hiểu là runtime đã triển khai. Cookie và challenge cũ trong v1/evidence cũ không bị thay bằng tìm-thay thế toàn repo.
