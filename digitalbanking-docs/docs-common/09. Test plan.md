## 1. Mục đích và phạm vi

### 1.1. Mục đích

Tài liệu này định nghĩa chiến lược kiểm thử để chứng minh Digital Banking MVP đáp ứng:

- Functional requirements và business rules.
- Strong transactional consistency.
- Idempotent transfer và retry safety.
- Authentication, authorization và ownership isolation.
- Immutable/auditable history và high traceability.
- Failure/recovery behavior.
- Performance, availability, observability và cost-related acceptance.
- Required demonstrations D1–D5 trong SRS và đề bài Project 4.

### 1.2. Trong phạm vi

- Unit, slice/component và service-level test.
- Database/integration test với PostgreSQL semantics.
- API contract/OpenAPI test.
- Concurrency and race test.
- Failure injection, restart, timeout và reconciliation test.
- Security, authorization, masking, secret/log hygiene và audit tamper test.
- Load/performance test với latency/error/invariant metrics.
- Test evidence, traceability, defect classification và acceptance decision.

### 1.3. Ngoài phạm vi

- Production penetration test hoặc independent security certification.
- Real financial transaction, CBS, payment gateway hoặc settlement.
- ML fraud model training/evaluation.
- Full browser/device compatibility matrix.
- Production capacity guarantee ngoài workload target đã nêu trong SRS.
- Runtime execution trong phiên docs-only này.

## 2. Test principles và trạng thái evidence

### 2.1. Principles

1. Test behavior against BR/FR/NFR/AC, not implementation preference.
2. Test transaction and locking behavior with database semantics matching design baseline.
3. Never use a mock to prove a database invariant, lock order, ledger balance or persistence guarantee.
4. Use synthetic data only (`NFR-032`, `TC-010`, `RC-005`).
5. Test duplicate, timeout, crash and dependency failure as first-class scenarios.
6. Assert both API output and financial/audit invariants.
7. Preserve correlation ID and evidence linkage across request, transfer, ledger and audit.
8. Do not call a test `Pass` without reproducible evidence.
9. Keep test IDs from source design documents; do not create duplicate IDs for the same behavior.
10. Record limitations explicitly. A blocked test is not a passed test.

### 2.2. Evidence statuses

| Status | Meaning |
|---|---|
| `Planned` | Test design exists; execution not claimed |
| `Implemented` | Test case code or executable test artifact exists; execution result is tracked separately |
| `Verified` | Evidence exists, scope and environment are recorded, expected result passed |
| `Blocked` | Execution cannot proceed because environment/data/dependency is missing |
| `Not accepted` | Evidence exists but acceptance threshold is not met |
| `Not verified` | No permitted evidence available |
| `Deferred` | Explicitly outside current milestone with reason and reopen trigger |

## 3. Test levels và strategy

| Level | Purpose | Scope | Required | Acceptance source |
|---|---|---|---|---|
| Unit | Pure rules and deterministic decisions | State machine, amount validation, idempotency decision, masking, fraud rule, canonicalization | Must for critical rules | `05` §5.6.1, `NFR-027` |
| Slice/component | Boundary behavior | Controller validation, error mapping, repository query and permission checks | Must | `05` §5.6.1, `07` §10 |
| Integration | Real transaction/data behavior | Transfer, ledger, lock, idempotency, audit, migration and recovery | Must | `NFR-009`–`NFR-012`, `design/02` |
| Contract | API compatibility | OpenAPI schema, status, header, error, pagination and replay semantics | Must | `07` §10, OpenAPI |
| Concurrency | Race and isolation behavior | Same-account transfers, opposite direction, daily limit and same-key requests | Must | D1, `NFR-009`, `NFR-010` |
| Failure/recovery | Partial failure and uncertainty | Credit failure, audit failure, timeout, DB loss, restart and reconciliation | Must | D3, `NFR-006`, `NFR-008` |
| Security/audit | Access and evidence integrity | IDOR, RBAC, masking, rate limit, tamper, audit coverage and export | Must | D4, `NFR-013`–`NFR-023` |
| Load/performance | Measured workload behavior | 20 RPS × 10 minutes, latency, error rate and post-load financial invariant | Must | D5, `NFR-001`–`NFR-004` |
| E2E/browser | Critical user journey | Login, transfer, history and audit UI | Should; dependency open | `05` §5.6.1, `docs-frontend/` |

### 3.1. Test pyramid

- Unit tests provide fast deterministic feedback.
- Integration tests prove PostgreSQL transaction, lock, constraint and migration behavior.
- Contract tests prevent API drift between semantic contract and machine-readable OpenAPI.
- Concurrency/failure tests prove distributed-system behavior that unit mocks cannot prove.
- Load tests measure target workload; they do not prove arbitrary production scale.
- E2E tests prove selected user journeys; they do not replace domain and integration tests.

### 3.2. Non-negotiable test rules

- Do not use H2 for transaction, locking, trigger, partial-index or PostgreSQL-specific behavior.
- Use disposable database state for integration tests.
- Use deterministic clocks, identifiers and synthetic data where test requires repeatability.
- Each concurrency worker uses an independent transaction/connection.
- Do not synchronize race tests with arbitrary sleep when a barrier/latch can express the condition.
- Run race tests repeatedly when checking flaky behavior.
- Test retry with the same idempotency key; a new key is a new business request.
- Never include password, OTP, token, secret or full account number in evidence.

## 4. Test environment and data contract

### 4.1. Environment matrix

| Environment | Purpose | Required properties | Evidence status |
|---|---|---|---|
| `local` | Manual API/UI checks | Synthetic demo data, safe local configuration | Planned |
| `test` | Automated unit/integration/contract/concurrency | Isolated PostgreSQL-equivalent semantics, deterministic setup | Planned |

Environment-specific implementation commands require `docs-backend/` and `docs-frontend/`; this document does not invent them.

### 4.2. Synthetic data rules

- No real customer data.
- IDs, names, phone numbers, email addresses and account numbers must be synthetic.
- Seed data must be reproducible and isolated from any real database.
- Test cleanup must not delete shared or production data.
- Evidence must show data classification and masking where relevant.

### 4.3. Test doubles and failure injection

| Dependency | Test method | Required behavior |
|---|---|---|
| OTP/notification gateway | Deterministic fake or controlled adapter | Timeout/error must map to defined auth/notification behavior |
| Fraud engine | Deterministic rule evaluator/fake | Fail-open or auto-block follows approved rule policy |
| Database connection | Controlled outage/failure injection | No false success; retry/reconcile by idempotency |
| Clock | Fixed/controllable clock | TTL, expiry and business-day boundaries are repeatable |
| Audit writer | Failure injection | No `COMPLETED` without required audit evidence |

Detailed failure injection depends on implementation documentation and `design/03`/`design/04`.

## 5. Test data and invariant contract

### 5.1. Transfer invariants

Every D1, D2, D3 and D5 test must check applicable invariants:

1. No account balance becomes negative.
2. Debit and credit are atomic for a completed transfer.
3. Ledger debit total equals ledger credit total per completed transfer.
4. Failed transfer leaves no unbalanced money movement.
5. One idempotency key/payload produces at most one business side effect.
6. Terminal transfer state cannot transition again.
7. Required money-movement audit coverage exists.
8. Retry after uncertain response does not create a second debit.
9. Customer cannot access another customer’s protected data.
10. PII is masked in response, log and notification evidence.

### 5.2. Parameterized boundary-value matrix

Use active server configuration for symbolic values. Do not treat an example value as a normative policy value.

| Rule | Boundary values | Expected assertion |
|---|---|---|
| Amount | `0`, negative, smallest valid unit, configured maximum, maximum + unit | Invalid values rejected; valid value creates only permitted effect |
| Decimal precision | 0, 1, 2 and more than 2 decimal digits | More than two decimal digits rejected per `BR-011` |
| Source/destination | Same account, different own account, different customer account | Self-transfer rejected; permitted ownership path succeeds |
| Balance | Amount equal to balance; amount greater than balance by smallest unit | Equal amount follows policy; excess amount never creates negative balance |
| Transaction limit | Configured limit - unit, equal to limit, limit + unit | Below/equal/above behavior follows active configuration |
| Daily limit | Remaining daily limit - unit, equal to remaining, remaining + unit | Concurrent requests cannot exceed configured daily limit |
| Large-value fraud | `T - unit`, `T`, `T + unit`, where `T` is active threshold | Boundary semantics and flag creation follow active fraud policy |
| High-frequency fraud | `N - 1`, `N`, `N + 1` events inside window `W` | Count and flag behavior follow active policy |
| OTP attempts | Attempts 1, 4, 5 and 6; expired challenge | Attempt limit, lock and expiry behavior match SRS |
| Idempotency | Same key/same payload; same key/different payload; expired key | Replay, conflict and retention behavior match API contract |
| Pagination | Empty, exact page size, page size + 1, invalid/expired cursor | Stable page boundaries and validation errors |

`T`, `N` and `W` are configuration symbols. Numeric fraud values remain dependent on `design/03. fraud-detection-rules.md`.

### 5.3. Data reset

- Reset only isolated disposable test state.
- Do not run destructive commands against a shared or real database.
- Concurrency tests must not use transaction rollback as the only cleanup mechanism because rollback can hide race behavior.
- Record database version, migration state and seed version in evidence.

### 7.6. Group F — D5 load and capacity

Target defined by SRS:

- 20 RPS for 10 minutes.
- Transfer p95 ≤ 2 seconds.
- Transfer p99 ≤ 5 seconds.
- Error rate < 1%.
- No negative balance, duplicate debit or ledger imbalance after load.

The D5 profile has two separate acceptance modes:

1. **Transfer-target mode:** 20 RPS of transfer-create requests for 10 minutes, used to verify the SRS transfer latency target. OTP-confirm traffic is a separate scenario because it has different lock, ledger and audit cost.
2. **Mixed-workload mode:** proposed endpoint mix below, used to characterize aggregate behavior. It does not replace transfer-target mode.

For error-rate measurement, expected business 4xx responses from intentionally invalid/retry/duplicate requests are reported separately and are excluded from the unexpected-error numerator. Unexpected 5xx responses, timeouts and transport failures count as errors. Report both total response distribution and unexpected-error rate.

Required report fields:

- Test environment and source revision.
- Workload profile, ramp-up, concurrency and endpoint mix.
- Authentication/session setup traffic separated from business traffic.
- Transfer-create ratio and OTP-confirm ratio recorded separately.
- Read/query ratio, invalid-request ratio and retry/duplicate ratio.
- Request count, success/error count and status distribution.
- p50/p95/p99 latency per endpoint group and overall.
- Pending transfer count and age.
- Database/lock/pool signals where available.
- Post-load financial and audit invariant result.
- Known limitation and whether result represents demo environment only.

Proposed initial profile, pending approval:

| Request group | Proposed ratio | Notes |
|---|---:|---|
| Auth/session setup | 10% | Setup traffic; exclude one-time setup from transfer latency where appropriate |
| Transfer create | 30% | Money-path intake and idempotency claim |
| OTP confirm | 20% | Lock, ledger, audit and terminal transition path |
| Transfer status/history | 25% | Read-heavy query path |
| Account/balance reads | 10% | Read path and ownership checks |
| Invalid/retry/duplicate cases | 5% | Expected 4xx reported separately from unexpected errors |

The proposed ratio is a workload assumption, not a confirmed requirement. Final mix must be recorded with the D5 report.

A load target without report and invariant query is `Not verified`, not `Pass`.

### 8.2. Exit criteria

A release/demo test cycle may be accepted only when:

- All Must AC and Must NFR have a passing result or approved explicit exception.
- D1–D5 evidence is reproducible and meets acceptance thresholds.
- A blocked D1–D5 item blocks acceptance of its corresponding Must criterion unless a documented exception is approved, including scope, reason, impact, owner decision and reopen trigger.
- No critical/high unresolved defect remains for demonstrated scope.
- No negative balance, duplicate debit, ledger mismatch or unexplained audit gap exists.
- Contract and schema checks pass.
- Security evidence has no unreviewed critical exposure.
- Test report records environment, source version, commands/procedures, expected and actual results.
- Known limitations and deferred Should requirements are documented.

### 8.3. Definition of Done

This document is complete when:

- Test strategy and levels are defined.
- Every SRS Must requirement is mapped to a test or explicit gap.
- D1–D5 have scenario, expected result and evidence contract.
- Defect, evidence and status rules are defined.
- Dependency section is current.
- No claim exceeds available evidence.

## 9. Defect management

### 9.1. Severity

| Severity | Examples | Release decision |
|---|---|---|
| Critical | Negative balance, duplicate debit, unbalanced ledger, PII/secret exposure, audit-chain corruption, unauthorized money movement | Block release |
| High | Incorrect transfer state, broken idempotency, failed authorization boundary, unrecoverable crash state, contract-breaking API error | Block affected scope |
| Medium | Incorrect non-critical filter, incomplete audit metadata, recoverable notification issue, observability gap | Fix or approved defer |
| Low | Documentation typo, cosmetic report issue, non-critical test readability | Track and fix by review |

### 9.2. Defect lifecycle

```text
Open → Triaged → Assigned → Fixed → Retested → Closed
                         ↘ Deferred with reason/reopen trigger
```

Severity controls release scope. Response-time SLA is intentionally deferred to [[digitalbanking-docs/docs-common/10. Master timelines.md]] and must not be invented in this test plan.

A failed test must identify whether cause is code, data, environment, dependency, test design or requirement. Do not change expected result only to make test pass.

## 12. Risks and open issues

| Risk | Impact | Mitigation | Reopen trigger |
|---|---|---|---|
| Concurrency tests are flaky | False failure or false confidence | Barriers/latches, independent transactions, repeated runs, invariant assertions | Any nondeterministic result |
| Test environment differs from demo | Evidence not representative | Record environment and repeat critical tests on demo topology | Configuration drift |
| Missing security/fraud design | Incomplete acceptance oracle | Keep dependency markers; do not sign off affected scope | Design docs completed |
| Numeric threshold assumption drift | Wrong fraud boundary result | Use symbolic `T`, `N`, `W`; verify active configuration before execution | Fraud design completed |
| Concurrent fraud evaluation race | Missed or duplicate flag | Run `T-FRAUD-08` with same-customer barrier and invariant assertions | Implementation failure or nondeterministic result |
| Load endpoint mix drift | D5 latency not representative | Record create and OTP-confirm ratios in report | Workload profile changes |
| Missing implementation docs | No exact command/class mapping | Keep contract-level test plan | Backend/frontend docs completed |
| Load evidence unavailable | NFR-001–NFR-004 unverified | Record Blocked/Not verified; define reopen conditions | Load environment and dataset available |
| Backup restore not exercised | RTO/RPO unknown | Schedule restore drill and record actual time/data loss | Backup and restore evidence available |
| Requirements change after plan | Traceability drift | Update source ID mapping and change log | BRD/SRS/API changed |
